# Pixel-loop — automated visual self-correction for pixel-perfect screens

> **Status: PROVEN reference recipe (graduated 2026-06-16).** Ran end-to-end on
> VenusX: all 41 Stage-1 screens generated + on-device reviewed through this flow.
> It is intentionally a **SCENARIO** (a chain of pipelines + host render), not a
> single container pipeline — the render step (gradle + Android emulator) is a HOST
> step, so a one-container pipeline only works on Linux+KVM (see "Render backend").
> Reference driver: `.hq/_runtime/scenarios/14-06-pixel-loop/scenario.ts` (resumable;
> env knobs SCREENS/MAX_ROUNDS/THRESHOLD/ASSETS). Sub-steps are real catalog
> pipelines: **gen-screen-llm** (generate/revise), **verify-visual** (LLM critic),
> **verify-screen-quality** (static defect lint), plus host materialize+render.
>
> ## How to run
> 1. Ensure inputs exist (screens.json, layouts/tokens, assets — see "Inputs").
> 2. From the workspace ROOT: `cd .hq/_runtime/scenarios/<run> && SCREENS="A,B,…"
>    MAX_ROUNDS=4 ASSETS=<manifest> bun scenario.ts` (copy the reference driver into
>    a fresh dated run dir first; it's resumable — re-run to continue).
> 3. After generation, gate with `verify-screen-quality` (HIGH=0) and review.
> The single-pass form we actually used in batches: run gen-screen-llm directly
> (`bun run pipeline run gen-screen-llm --input=…`), materialize files.json into the
> app, run verify-screen-quality, review on device. The full emulator revise-loop
> (scenario.ts) is for unattended convergence.

## What it accomplishes / when to reach for it

Turns the **functional** RN/Expo screens (already generated by the factory) into
**pixel-faithful** ones, automatically, by closing a visual feedback loop:
generate a screen from its Figma target → render it on a real Android emulator →
have a multimodal LLM critic compare render-vs-Figma → feed the diff + notes back
into regeneration → repeat until it passes. No human eyeballing in the loop; the
critic writes its own fix-notes.

Reach for this as **Phase B** of the mobile factory, after the functional app
exists (scaffold + api + nav + screens + backend compile & run). Input is a set
of screenIds to perfect; output is materialized pixel screens in the app worktree
that a visual critic certifies as faithful to Figma.

This is the iterative, "expensive" phase (LLM vision + emulator builds), so it's
run as its own focused effort, in batches, not on every edit.

## The flow

```mermaid
flowchart TD
  gen[gen-screen-llm  (revise if round>1)] --> mat[materialize files.json into app worktree]
  mat --> build[gradle assembleRelease → APK]
  build --> shoot[install + deep-link + full-page screencap per screen]
  shoot --> verify[verify-visual: content-aware coverage + LLM critic]
  verify -->|all pass| done[done]
  verify -->|some fail| revise[write revise.json; freeze-pass the rest]
  revise --> gen
```

Read it as: **rounds are sequential**; **within a round screens fan out**
(gen-screen-llm + verify-visual both process the screen set with internal
concurrency). Each round only regenerates screens that have NOT yet passed
(freeze-passed). Loop until allPass or MAX_ROUNDS.

Two of the steps are **containerized pipelines** (`gen-screen-llm`,
`verify-visual`); the rest (materialize, gradle, emulator screencap, loop control)
are **host** steps in the driver. See "Render backend" below — that host/container
split is the central design question for graduation.

## Pipelines used

- **gen-screen-llm** — multimodal LLM authors one RN screen (flexbox, not absolute)
  from: the Figma frame image + the layout IR (figma-design `layouts.json`) +
  design tokens + the real exported assets manifest (gen-assets) + our component
  conventions. Revise mode also takes the previous render + diff + critic notes.
  Output: `files.json` (path→content map, component + styles per screen + barrel).
- **verify-visual** — per screen: downloads the Figma reference (webp) from the
  inventory site, computes a content-aware coverage metric (best-effort), and runs
  a multimodal LLM critic that returns `{verdict, notes}`. Emits `verdict.json`
  (all screens) + `revise.json` (failed screens, in gen-screen-llm's revise shape)
  + `report.md`. Gate: pass = critic==pass AND (coverage null OR ≥ threshold).
- Upstream artifacts reused (not re-run each loop): `merge-spec-design` screens.json,
  `figma-design` layouts.json + tokens.json, `gen-assets` assets-manifest.json.

## LLM on the Claude SUBSCRIPTION (not paid OpenRouter)

Both LLM pipelines route through the Claude **subscription** via the Agent SDK,
because the prepaid OpenRouter balance kept 402-ing and per-token vision is
expensive at fan-out scale.

- Model id `anthropic/claude-sonnet-4-6` → `ctx.ai.agent` routes to
  `@anthropic-ai/claude-agent-sdk`. Auth = `CLAUDE_CODE_OAUTH_TOKEN` in
  `.hq/pipelines/.env` (1-year token from `claude setup-token`, run in a REAL
  terminal — `! claude setup-token` from the session hangs, no TTY). The runner
  passes env into the container; stale `~/.claude/.credentials.json` was deleted.
- **Vision via the SDK = the agent Reads image files itself.** We write the images
  into a per-screen `cwd` and call
  `ctx.ai.agent(model, {cwd, allowedTools:["Read"], prompt, maxRetries:2})`; the
  prompt tells the agent to `Read "figma.webp"` (+ render/diff on revise). The
  Read tool **decodes webp directly** — no host PNG conversion needed for the LLM.
  (The numeric metric still needs an optional host-converted PNG; pngjs can't read
  webp. That's best-effort; the critic is the real judge.)
- gen-screen-llm: `buildAgentPrompt()` in `lib/prompt.ts`; 002-generate writes
  figma.webp/render.png/diff.png into the cwd, parses two fenced blocks from
  `r.result` via `parseCodeBlocks`.
- verify-visual: `runCritic(ai, model, workDir, …)` + `buildCriticAgentPrompt()` in
  `lib/critic.ts`; writes figma.webp+render.png into a per-screen workDir, agent
  returns verdict JSON.
- Both: config model → `anthropic/claude-sonnet-4-6`, `requireEnv` →
  `CLAUDE_CODE_OAUTH_TOKEN`. The old `queryMultimodal`/`lib/llm.ts` (OpenRouter
  data-URL fallback) is now dead code.
- Caveat: Max subscription has ~5h usage windows — a big fan-out may hit them
  (whereas OpenRouter was pure $). Cost numbers in logs (~$0.4/screen) are
  *notional* token estimates; actual usage is against the subscription quota.

## The 5 convergence fixes (hard-won — keep ALL of them)

1. **Dynamic test harness.** The driver regenerates `App.tsx` each round to
   register EXACTLY the screens under test as a flat stack + deep-links. A static
   harness left un-registered screens deep-linking to the initial route → the
   critic correctly screenshotted the splash and flagged "completely different
   screen". (App.tsx.orig is saved to restore the real app.)
2. **Coverage is an anti-catastrophe FLOOR, not a fidelity gate.** Content-aware
   coverage (similarity over non-bg pixels) is still a pixel diff, so text-heavy
   screens score low (~0.10–0.29) even when faithful (subpixel font raster
   differs). Threshold 0.03–0.1 only catches empty/broken (~0). **The LLM critic
   is the real fidelity judge.** Do NOT raise the threshold to gate fidelity.
3. **Freeze-passed.** The driver tracks a `passed` Set; each round regenerates
   ONLY not-yet-passed screens. Without this, already-passed screens get re-rolled
   and DEGRADE (saw CycleAddSymptoms pass→fail).
4. **max_tokens 48000** in gen-screen-llm (was 16k). Long multi-section screens
   (e.g. ProfileMain, 5 sections) were truncated at 16k → "missing sections".
   48k is still under the 64k default that caused OpenRouter affordability 402s.
5. **Full-page adaptive screenshot.** Device captured only the visible ~844px
   while a screen is ~3800px → critic saw "missing sections" (below the fold).
   Fix: download the Figma ref first, read its aspect, set `adb wm size 1080x<H>`
   + `wm density 440` (~390dp) so the WHOLE screen renders in one frame matching
   the Figma frame proportions; relaunch the deep link; screencap; reset after.

## Generator-quality fixes from the on-device review (2026-06-15) → FOLD INTO GENERATORS

The visual-diff critic only judges "structurally faithful" — it does NOT catch
mocks-rendered-literally, dead interactivity, or device-relative layout. A manual
on-device iOS walk of the 23 ready VenusX screens surfaced these systemic defects.
They were patched BY HAND in the venusX worktree for the review; each must be folded
back into `gen-screen-llm` (prompt) and/or `scaffold-app` (template) so future apps +
the remaining screens get them for free. See memory `[[gen-screen-pixel-defects]]`.

Defect → fix:
1. **Fake status bar / "9:41".** Figma mocks a phone status bar; the generator put a
   hard-coded `<Text>9:41</Text>` (+ fake battery/wifi) into ~40/51 screens. The OS
   renders the real status bar. → gen-screen-llm prompt: NEVER emit a status-bar mock
   or a hard-coded time; strip the whole mock row.
2. **Static-text "inputs".** Fields drawn pre-filled in Figma ("anna.petrova@email.com",
   "••••••••", "Введите …") were rendered as static `<Text>` inside an input box → not
   typable. → any field-shaped element with placeholder/example text must be a real
   `<TextInput>` (secureTextEntry / keyboardType / autoCapitalize as fitting), backed by
   useState (value + onChangeText), and the TextInput must be `flex:1` so the whole field
   is the tap target (a non-flex TextInput collapses to a tiny hit area).
3. **Non-interactive selection lists.** Radio/checkbox option lists were static `<View>`
   rows with ONE option hardcoded "selected" (a different selected-vs-unselected SVG) and
   no state → nothing selectable. → fold the hardcoded option into one array; useState
   (string for single / string[] for multi); each option a `<TouchableOpacity>` that
   toggles selection; render selected vs unselected icon by state (or an `optionSelected`
   style if only one icon exists). Bottom nav back/next must be TouchableOpacity, not View.
4. **Eye-toggle not wired.** Password field had an eye button with no handler. → wire a
   `showPassword` state to `secureTextEntry={!showPassword}` + onPress toggle.
4b. **Selected-state style not visually distinct.** The generator made the
   `pillActive`/`optionSelected` style nearly identical to the base (same bg/border), so a
   selected chip looks unselected (CycleAddSymptoms: `pillActive` had the same lavender bg).
   The design shows selected = FULL fill `#2c1332` + white text. → the selected variant must
   be clearly different (filled primary bg + inverted text), derived from tokens, not a
   near-copy of the base. (Fidelity defect the visual critic should also catch.)
5. **Literal Figma Y as paddingTop.** Absolute canvas Y copied into `paddingTop` (e.g.
   255 on Welcome, 42–54 on auth) → huge empty gap on taller real devices + collapsed
   `flex:1` spacers (buttons stick together). → use relative spacing/`gap`, never absolute
   canvas coordinates; don't pour leftover height into the TOP; keep the design's vertical
   rhythm (equal gaps where the design has equal gaps).
5b. **Theme background/surface mapping is inverted.** apply-design-tokens set light
   `background:#ffffff, surface:#e8e0ec`, but the design's PAGE canvas is lavender
   `#f5f0f7` and WHITE is the card/surface color. Most screens hide this by hardcoding
   `container backgroundColor:#f5f0f7`, but any screen that relies on the theme fallback
   (e.g. MedcardHome called `<ScreenContainer>` with NO style) came out white. → fix in
   apply-design-tokens: light `background:#f5f0f7, surface:#ffffff` (done locally in
   venusX themes.ts). Don't pick the most-frequent fill as page bg — the white card fill
   dominates pixel count but the canvas is the lavender.
5c. **Cards lack shadows.** Generated card/list-item containers (white, rounded) miss the
   soft elevation the design shows — same defect class as inputs (#7) but for cards. →
   give card containers a subtle shadow, e.g. `shadowColor:'#000', shadowOpacity:0.08,
   shadowRadius:12, shadowOffset:{0,4}, elevation:3` (lighter than the input shadow).
5d. **Shadows/cards should be DESIGN TOKENS + a shared component, not per-screen inline
   (user, 2026-06-15).** The factory currently hand-writes shadow props inside each
   screen's StyleSheet and re-declares the white-rounded "card" look per screen — so a
   tweak means editing dozens of files and screens drift. The RIGHT approach the user
   called out: define elevation as a TOKEN once and apply it through a SHARED component.
   Concretely:
   - **apply-design-tokens** → emit `theme/shadows.ts` with `SHADOW.card` / `SHADOW.input`
     elevation tokens (DONE locally in venusX: `src/theme/shadows.ts`, exported from
     `theme/index.ts`, alongside spacing/typography tokens).
   - **scaffold-app** → ship shared `<Card>` (and `<Input>`) components in the component
     library that consume those tokens (white surface + radius + `SHADOW.card`), so the
     card look is defined ONCE.
   - **gen-screen-llm** → render groupings as `<Card>` and fields as `<Input>` instead of
     re-styling inline; spread `SHADOW.card`/`SHADOW.input` where a raw style is needed.
   Status: token file added in venusX; existing generated screens still use inline shadow
   (Medcard/Cycle patched by hand for the review). Full migration to `<Card>`/tokens is a
   generator change to land before fan-out — then every card across the app gets the
   shadow from one place. This is the model for ALL repeated visual primitives (cards,
   inputs, chips, list rows), same spirit as hoisting shared chrome (tab bar / header).
6b. **Keep the BOTTOM safe-area inset** (`edges={["top","bottom"]}`). An earlier pass
   dropped the bottom edge (edges top-only) thinking it "covered content" — but that was
   really the white-band bug (fixed by full-bleed bg, #6). Without the bottom inset, bottom
   buttons sit flush against the very screen edge / under the home indicator (too low). With
   it + full-bleed bg, the button sits above the home indicator and the bg fills the strip —
   matching the design. Fixed in venusX ScreenContainer + scaffold-app template.
6. **Safe-area background.** Screen bg must fill the WHOLE screen edge-to-edge (under
   status bar + home indicator); only CONTENT is safe-area inset. → DONE in venusX
   `ScreenContainer`: paint bg on an outer full-bleed View, keep SafeAreaView transparent,
   and use `edges={["top"]}` (drop bottom so content isn't clipped). FOLD INTO scaffold-app's
   ScreenContainer template.
7. **Input field vertical centering — and NO shadow.** Generated input text sat too low →
   remove `lineHeight` + add `textAlignVertical:"center"` + `paddingVertical:0` on the
   TextInput text style. IMPORTANT (user rule, 2026-06-15): TEXT-INPUT FIELDS are FLAT —
   border only, NO shadow. Only cards / info-display blocks get the shadow (see 5c). An
   early pass mistakenly added `SHADOW.input` to input wrappers; it was reverted app-wide.
   (The SHADOW.input token still exists in the theme but is currently unused — inputs flat.)
8. **Single-word back button wraps ("Назад" → "Д" on next line).** `alignSelf:"flex-start"`
   shrinks the touchable to a measured intrinsic width that is sometimes 1px short → last
   glyph wraps. → add `numberOfLines={1}` to short single-line labels (back buttons etc.).
9. **Buttons stretched to full width when the design has a fixed/narrower width.** The
   survey bottom nav next-button was `flex:1` (filled to the edge), but Figma has it
   FIXED: 390 frame → NavButtons section 346 (22px side margins), back 52, **gap 60**,
   next **234**. The generator dropped the real 60px gap to 12 and made next flex, so it
   grew ~44px wider than design. → respect the IR's gap and intended button width. Cheap
   responsive fix that reproduces it exactly on a 390 device AND scales: set the row's
   `gap` and side `paddingHorizontal` from the IR (here gap:60, padding:22) and KEEP next
   `flex:1` — that yields exactly 234 at 390px. (Or hardcode the IR width if a true fixed
   width is wanted.) GENERAL LESSON for gen-screen-llm: don't default sibling buttons to
   `flex:1`; carry the IR's inter-element gaps and element widths — full-bleed is the
   exception, not the default.
   FOLLOW-UP (user preference, 2026-06-15): the survey bottom nav should be a CENTERED
   GROUP, not edge-spread. Final layout applied to all 10 survey screens: row
   `justifyContent:'center'`, `gap:16`, back 52, next fixed `width:234` (no flex) → the
   [back+next] cluster (302px) is centered with equal side spacers (~44px on a 390 device).
   The Figma IR had them edge-spread (gap 60, back left / next right); the user overrode
   that to a centered cluster — a reminder that IR fidelity is the default but explicit
   user layout preferences win, and the critic can't infer them.
10. **Sticky bottom action on long screens.** A primary bottom button (Сохранить/Далее)
   on a long scrollable screen must be OUTSIDE the ScrollView as a fixed footer
   (ScrollView flex:1 → footer View w/ button), not the last child inside it (scrolls
   away). Hit on CycleAddSymptoms + CycleEditSymptoms. Folded into the prompt (#4c).
11. **No emoji as icons.** The generator put a 👁 emoji eye-toggle on a password field
   that has no eye in the design (ProfileDeleteConfirm). Never use a colorful emoji as an
   icon — use a real exported asset or omit. Folded into the prompt (#4) + checker (#11).

Where the per-screen handoff goes: screen-level fixes live in the venusX worktree now;
the durable home is the generator prompt/template. Until folded in, the REMAINING screens
(profile change-email/password flows, settings, cycle/add-trackers) still have defects
#2/#3 (static-text inputs, non-interactive lists) — they were out of the 23-screen review
scope. Re-run them through the loop AFTER the generator is improved, or they'll need the
same hand-patching.

## Shared app chrome — the bottom tab bar (architectural, spans 3 pipeline stages)

The design has a **persistent bottom navigation tab bar** on the main app —
exactly 4 tabs, fixed order: **Медкарта · Цикл · Тренды · Статьи** (NOT Home or
Profile — those are reached another way, e.g. the top menu). This is ONE shared
chrome component for the whole app, not per-screen content. The factory currently
gets this wrong at every stage:

1. **analyze-tz / merge-spec-design** — the contract `screens.json` flags ALL 51
   screens as `type:"stack"`; ZERO are `type:"tab"`. So the tab set is never
   identified upstream. → the spec/contract must classify which screens are the
   bottom-tab roots (and in what order), e.g. populate `type:"tab"` + a tab order/
   icon. The schema ALREADY has a `type: "tab"|"stack"|"modal"` field — it's just
   never set.
2. **gen-navigation** — builds `MainNavigator` as a FLAT `createNativeStackNavigator`
   with every screen; there is NO `createBottomTabNavigator`. → it should emit a
   bottom-tab navigator for the `type:"tab"` screens, with the rest as stack screens
   pushed over the tabs. (react-native bottom-tabs is already a dep.)
3. **gen-screen-llm** — bakes the tab bar as STATIC JSX into ~11 screens
   (HomeHome, MedcardHome, MedcardAddMenu, CycleMain, TrendsDashboard, ArticlesList,
   ArticlesDetail, ProfileMain, Settings*). It's duplicated, non-functional, and
   would DOUBLE UP with a real tab bar once nav is wired. → gen-screen-llm must be
   told the bottom tab bar is app chrome (rendered by the navigator) and NOT draw it
   per screen; it should render only the screen's own content above the tab area.

Net: a single `BottomTabNavigator` (Медкарта/Цикл/Тренды/Статьи) styled to match the
Figma tab bar, rendered once; per-screen static tab bars removed. Same pattern likely
applies to other shared chrome the designer repeats per frame (top app bar / header
with "Анкета"/Light/RU, the menu button) — detect repeated cross-screen chrome and
hoist it into navigators/layout components instead of regenerating it on every screen.
For VenusX this is deferred (the review harness shows screens standalone; the static
bars are harmless there) but MUST be handled before the screens are wired into the real
app, and is a first-class pipeline requirement going forward.

## Common-defects CHECKER (lint) → future `verify-screen-quality` pipeline

A static checker that encodes the recurring defects above lives at
`.hq/scenarios/pixel-loop/check-screen-defects.ts`. Run on any generated app:

    cd <app> && bun .../check-screen-defects.ts src/screens

It scans every screen + styles file and reports candidates by rule (HIGH/MED/LOW),
mapped to the numbered defects in this doc. Rules currently encoded:
- **#0 undefined-component** (HIGH) — a PascalCase JSX tag used but never imported or
  defined → runtime crash on render (SIGABRT "Element type is invalid"). transpile/tsc-
  free checks MISS this (it's a runtime ref error, not syntax). Caught the deactivate-
  screen crash after an import was accidentally dropped. (Excludes TS generics like
  `useState<Set<…>>` via a JSX-delimiter regex + a TS-builtins allowlist.)
- **#1 fake-statusbar** (HIGH) — hard-coded "9:41" status-bar time.
- **#11 emoji-icon** (MED) — a COLORFUL emoji used as a UI icon (e.g. 👁 eye-toggle the
  generator invented on a password field that has none in the design, 🙈/🗑/📅). Use a
  real exported asset or omit. Excludes monochrome UI glyphs (✕ close, ✓ check, ‹›←→).
- **#2 static-text-input** (MED) — placeholder-like text in a `<Text>` (dead input?).
- **#2b input-not-filled** (MED) — field box with `alignItems:'flex-start'` → the
  TextInput won't fill width (tap only on left / clipping).
- **#3 dead-options** (HIGH) — pressables rendered in a `.map()` that reference a
  selected/active style but have ZERO `onPress` → selection chips/radios/checkboxes
  that show selected state but can't be toggled (e.g. CycleAddSymptoms pills, the
  survey selectors before they were wired). Deliberately does NOT flag one-off CTA
  buttons without onPress — pixel screens are presentational and get handlers wired
  later; only repeated option groups with a selection style are the bug.
- **#4 input-text-low** (MED) — input text style has `lineHeight` but no
  `textAlignVertical:'center'` (text sits below center).
- **#5 literal-Y-padding** (MED) — `paddingTop > 200` (likely a literal Figma Y).
- **#5c card-no-shadow** (LOW) — white rounded card without a shadow.
- **#7 input-has-shadow** (MED) — input field wrapper WITH a shadow. Inputs must be flat
  (border only); shadows are ONLY for cards / info-display blocks (user rule).
- **#8b back-narrow** (MED) — back '‹ Назад' text slot (text OR its container) with a
  fixed width < 80 → wraps, or with numberOfLines truncates to "‹ Наз…". Fix: size to
  content + flexShrink:0 (don't pin a tiny width; in a centered-title header use
  [back(content) | title flex:1 | balancer]). Excludes icon back buttons (square with
  borderRadius+height). Found this on 4 screens (incl. AuthSuccess from the first 23).
  NOTE: numberOfLines={1} on a back label is a TRAP — it converts a 1px-short wrap into
  a visible truncation; prefer content sizing + flexShrink:0 and DROP numberOfLines on
  back labels.
- **#9 button-flex1** (LOW) — primary/next button with `flex:1` (confirm vs design).
- **chrome bottom-tab** (MED) — bottom-tab label baked into a screen (should be a
  shared navigator, not per-screen).

It is conservative (flags candidates to eyeball, with false positives — e.g. a
"Введите код" heading, a "Выберите клинику" picker, a static unit label). Exit code
is non-zero on any HIGH finding, so it can gate a build. **Graduate this into a real
`verify-screen-quality` pipeline** that runs after gen-screen-llm (alongside the
visual critic): the critic judges fidelity, this catches the mechanical defects the
critic misses (dead inputs, fake chrome, non-fills). Extend it as new recurring
defects surface. Last run on VenusX after the normalize pass: 0 HIGH; remaining MED/LOW
are the deferred shared-tab-bar item + known false positives.

A one-shot normalizer (`/tmp/normalize.ts` during the review) applied app-wide:
white "card" styles → +card shadow; `input*` text styles → drop `lineHeight`, add
`paddingVertical:0` + `textAlignVertical:'center'`; field boxes → drop
`alignItems:'flex-start'`. That fixed 12 cards + 9 input-text styles at once — the same
transforms the generator/`<Card>`+`<Input>` components should bake in.

## Gotchas (things that bit us)

- **Subscription Agent SDK STALLS on very heavy screens.** gen-screen-llm on the
  Claude subscription aborts a screen if the agent emits no SDK events for ~300s
  ("stall detected: idle > cap — aborting"). Screens with a big layout IR (e.g.
  MedcardAddMenu hit `ctx 37k` vs 22–25k for others) make the agent generate a long
  output with no intermediate events and trip the 300s cap — deterministically (failed
  3× incl. solo retries). Most screens are fine; the 1–2 heaviest per batch may need:
  re-run later, a trimmed IR (cap node depth/count), a bumped stall cap in the agent
  runner, or the OpenRouter `query` path (no stall guard) for that one screen. Batch 2
  shipped 8/9 this way; MedcardAddMenu deferred. Plan around 1–2 stragglers per ~9.
  **FIX applied (2026-06-15):** the agent SDK runner (`@hq/core ai/claude.ts`) exposes
  `inactivityTimeoutMs` (default `DEFAULT_INACTIVITY_TIMEOUT_MS` = 300_000); it passes
  through `ctx.ai.agent(model, {...})` via `...rest`. gen-screen-llm 002-generate now sets
  `inactivityTimeoutMs: 600_000` so heavy screens that legitimately idle >300s while
  generating a long output aren't aborted. (NOTE: changing pipeline CODE requires a
  `BUILD=1 bun run pipeline run …` to rebuild the dev OCI image — the run is containerized.)
- **Run from the WORKSPACE ROOT, not `.hq/pipelines`.** The root `pipeline` npm
  script sets `--workspace=$PWD --runtime-dir=$PWD/.hq/_runtime`, so input paths
  under `.hq/_runtime` are inside the container bind. Running from `.hq/pipelines`
  → ENOENT (paths outside the bind). The driver does `$\`bun run pipeline …\`.cwd(WS)`.
- **screenId derivation = the driver's `pascal()`** (split on non-alnum,
  capitalize first letter, KEEP internal caps). Routes are camelCase →

## Render backend — the central graduation decision (user, 2026-06-15)

The graduated pipeline must run **both on a Mac and as a service on a server**.
Abstract the render step behind ONE contract and pick the engine by environment:

```
render(input) → output
  input:  { files | prebuilt APK, screens:[{screenId, route/deepLink, figmaAspect}] }
  output: { screenId → screenshot.png }
```

The loop (gen → render → verify → revise → freeze) calls this and is agnostic to
HOW the screenshot was produced.

| backend | runs on | mechanism | when |
|---|---|---|---|
| `host` | Mac or Linux host | gradle + local emulator (Hypervisor.framework on Mac / KVM directly on a Linux host) — **what the scenario does today** | dev on Mac; a server where the SDK lives on the host |
| `container` | **Linux + KVM only** | emulator baked into the image, `/dev/kvm` passed into the container | self-contained pipeline-as-a-service on Linux |
| `cloud` | **anywhere** | EAS build → Maestro Cloud (proven — smoke passed on Pixel 6) | universal fallback; Mac without local SDK; any CI |

**Why emulator-in-container is Linux-only:** on Linux a container shares the host
kernel and can be given `/dev/kvm` → accelerated emulator inside the container. On
macOS, Docker runs inside a Linux VM and Docker Desktop does NOT expose `/dev/kvm`
to containers (no usable nested virt on Apple Silicon), so `container` can't work
on a Mac. The emulator works **on the Mac host** (which is what we use today) —
just not inside a container there. `cloud` sidesteps the whole Mac-vs-Linux
problem (works identically everywhere) at the cost of money + latency, so it's the
natural universal mode; host/container are faster/cheaper local optimizations.

Selection: config knob `renderBackend: auto | host | container | cloud` (default
`auto`): (1) local emulator/adb present → `host`; (2) Linux && `/dev/kvm` present →
`container`; (3) `EXPO_TOKEN` + `MAESTRO_CLOUD_API_KEY` set → `cloud`; (4) else a
clear "configure one of the three" error. Operator can always force a specific one.

EAS/Maestro tokens already in `.env` (`EXPO_TOKEN` robot "HQ", Expo account
`nikita36trintas-team`; `MAESTRO_CLOUD_API_KEY` rb_…). EAS projectId
`c26e9729-7976-4632-af58-d80ea468569a`. Maestro needs Java 17 on PATH; cloud trial
