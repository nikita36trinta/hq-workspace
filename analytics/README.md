# Analytics — переиспользуемый пайплайн продуктовой аналитики

Автономный вендор-модуль (как `mailer`): копируется в проект, работает без внешних
зависимостей. Каждый проект — самостоятельная единица со **своим** дашбордом и
хранилищем. Общий только сам пайплайн (этот код).

## Что даёт
Воронка (уники по сквозному id) · отвал на загрузке по секундам · денежная петля
(клик → шлюз → оплата) · take-rate апселла и AOV · **NET-маржа и CB-rate по варианту
цены** (не gross!) · метод оплаты · объект/превью → конверсия (лифт) · трение формы ·
LTV/повторные покупки. Всё опционально — не задал в конфиге, не считается.

Заложено по best-practices аудиту: меряем NET, а не gross; сквозной persistent id
(отложенная оплата/retention); пост-оплатный слой; тег вариант/метод/источник.

## Файлы
- `analytics.py` — FastAPI-роутер + агрегация (`make_router`, `AnalyticsConfig`).
- `analytics_render.py` — HTML-рендер дашборда.
- `analytics.js` — фронт: `Analytics.goal()`, сквозной device-id, visit, abandonment-beacon.

## Подключение (бэкенд)
```python
from analytics import make_router, AnalyticsConfig

ANALYTICS = AnalyticsConfig(
    project_id="sdelka",
    data_dir="/app/data",
    admin_token=os.getenv("ADMIN_TOKEN", ""),
    title="ЧистаяСделка · аналитика",
    funnel=[("visit","Зашли"),("checkout_open","Открыли форму"),
            ("check_started","Запустили проверку"),("check_completed","Дождались"),
            ("pay_click","Нажали оплатить")],
    money=[("pay_click","Нажали оплатить"),("yookassa_reached","Дошли до ЮKassa")],
    roles={"obj_split":"check_started","abandon":"check_abandoned",
           "friction":"checkout_abandon","lift":"preview_object","bump":"pay_click"},
    price_variants={"A":299,"B":490,"C":690,"D":5299},   # опц., для NET/A-B
    payments_provider=lambda: read_payments(),           # опц., для денег/LTV/NET
    since_provider=lambda: read_since(),                 # опц., отсечка сброса статистики
    cogs_provider=lambda: read_cogs(),                   # опц., себестоимость per-order
    heartbeat_event="check_heartbeat",                   # опц., секунда ухода (см. ниже)
    campaign_cookie="cs_camp",                           # опц., матрица кампаний + drill-down
    exclude_campaigns={"sdelka_rsya"},                   # опц., выкинуть кампанию из статы
    signal_labels={"cta_click":"Клик по CTA"},           # опц., «Прочие сигналы» (уники)
    stamp_device=True,                                   # срез устройство/ОС/браузер из UA
    stamp_cookies={"cs_src":"src","cs_v2":"ab"},         # куки → поля события (источник, плечо A/B)
    derive_fields=lambda name, body: {...},              # опц., проектный срез (напр. регион объекта)
    extra_kpis_provider=lambda ctx: [...],               # опц., доп-плитки в сводку
    panels_provider=lambda ctx: [...],                   # опц., произвольные панели
)
app.include_router(make_router(ANALYTICS))
```
Роуты: `POST /api/goal`, `GET /admin/stats?token=…[&src=][&campaign=]`, `.../stats.json`,
`GET /admin/selfcheck?token=…` (диагностика подключения).

### Матрица кампаний + drill-down (2026-07)
Задай `campaign_cookie` (кука с меткой utm_campaign, ставится на лендинге) → каждое событие
штампуется кампанией. В дашборде появляется **матрица**: строка на кампанию × вехи воронки +
деньги (визиты→оплаты→выручка→CVR→ср.чек). **Клик по кампании фильтрует ВЕСЬ дашборд** на неё
(`?campaign=X`) — воронка, деньги, отвал, риск, A/B-цена. `exclude_campaigns` — выкинуть слабую
кампанию из статы совсем (метка липкая, поэтому её first-touch посетители капают и после паузы).

### Секунда ухода (heartbeat, best-practice)
Задай `heartbeat_event` + `roles["completed"]`. Фронт (`analytics.js`), пока экран загрузки
ВИДЕН, шлёт пинг с `sec` раз в 5с; сервер берёт `max(sec)`=last-seen → секунда ухода даже когда
финальный beacon не дошёл (мобильный дроп). Точность ±интервал. Одиночные exit-события доходят
лишь 68–91%, поэтому heartbeat — основа. `beforeunload`/`unload` НЕ используем (ломают bfcache).

### payments_provider — интерфейс платежа (dict)
```
{ "status":"succeeded", "amount":490, "email":"…", "ts":"<iso>",
  "variant":"B", "method":"sbp",            # опц. для NET/метод
  "order":"…",                              # опц. для стыковки COGS
  "refunded":true, "refund_amount":490,     # опц. NET
  "chargeback":true, "cb_amount":490, "fee":17 }  # опц. NET (fee дефолт ~3.5%)
```

## Подключение (фронт)
```html
<script>window.ANALYTICS_CONFIG = {endpoint:'/api/goal', metrika:110382224};</script>
<script src="/static/analytics.js"></script>
```
Использование:
```js
Analytics.goal('checkout_open', {tariff:'base'});
Analytics.goal('check_started', {object: userInput});   // obj → address/cadastre авто
Analytics.startLoading();                                // начало загрузки результата
Analytics.stopLoading();                                 // дождался (уход не считаем)
Analytics.goal('pay_click', {bump: 1});
Analytics.goal('yookassa_reached', {});
```
Автоматом: `visit` при загрузке, сквозной `device-id` (localStorage), отвал на
загрузке через `sendBeacon` при закрытии/переключении вкладки.

## Роли событий (config.roles)
| роль | что несёт | пример события |
|---|---|---|
| obj_split | поле `object` → address/cadastre | check_started |
| abandon | поле `sec` (финальный beacon ухода) | check_abandoned |
| completed | «дождался результата» (кто НЕ ушёл) | check_completed |
| friction | поле `fields` (заполненные поля) | checkout_abandon |
| lift | поле `shown` (показан объект/превью) | preview_object |
| bump | поле `bump` (взяли апселл) | pay_click |

## Секунда ухода: heartbeat (best-practice)
Одиночные exit-события (`pagehide`/`visibilitychange`) доходят лишь в ~68–91% (мобильный
дроп, отошёл-не-закрыл). Поэтому основа — **heartbeat**: `analytics.js`, пока экран загрузки
ВИДЕН, шлёт пинг `heartbeat_event` с `sec` раз в `heartbeatMs` (деф. 5000). Сервер берёт
`max(sec)` по сессии = last-seen. Финальный beacon (роль `abandon`) на `visibilitychange`/
`pagehide` уточняет последний интервал. `build_dashboard`:
`секунда ухода = max(финальный beacon, last-seen heartbeat)`, дождавшихся (`completed`)
исключает, свежие (ещё грузятся, <180с) не считает. Точность ±интервал. Подключение:
`heartbeat_event="check_heartbeat"` + `roles["completed"]="check_completed"`; фронт сам
пингует внутри `Analytics.startLoading()`/`stopLoading()` (гейт по видимости, без Метрики).
`beforeunload`/`unload` НЕ используем (ненадёжны, ломают bfcache). Ресёрч: 2026-07.

## Проектные добавки в дашборд (панели и KPI)

Всё на ОДНОЙ странице `/admin/stats`. Модуль остаётся агностичным: проект отдаёт
структурированные данные, модуль рендерит их своим единым стилем. Два опциональных
провайдера в конфиге (оба получают `ctx = {"src", "token"}` на каждый запрос):

```python
AnalyticsConfig(
  ...,
  extra_kpis_provider=lambda ctx: [               # доп-плитки в верхнюю сводку
    {"label": "NewDB баланс", "value": "420 ₽", "sub": "...", "tone": "bad"}],
  panels_provider=lambda ctx: [                   # произвольные карточки
    {"title": "A/B-тест цены", "icon": "spark", "tag": f"источник: {ctx['src']}",
     "controls": [{"label": "Всё", "href": "?src=all", "active": True}, ...],   # сегмент-переключатель
     "banner": {"tone": "ok", "text": "<b>Готовность:</b> ..."},                # ok/warn/bad/info
     "table": {"head": [...], "rows": [[cell, ...]]},                           # ячейки можно с HTML
     "kv": [["ключ", "знач"]], "chips": [["метка", "N"]], "bars": [["метка", N]],
     "tiles": [{"v": 40, "k": "Визиты"}],                                       # стат-плитки
     "hint": "сноска"}],
)
```
Панели рендерятся полной шириной в начале сетки. Порядок блоков внутри панели:
controls → banner → tiles → table → kv → chips → bars → hint. `ctx["src"]` берётся из
`?src=` — так работает переключатель источника трафика (реклама/органика/всё), меняя
данные панели без отдельной страницы. Пример — sdelka: A/B-тест цены + продажи по тарифам
+ вовлечённость (Метрика) — раньше жили на отдельном `/admin/ab-stats`, теперь одна страница.

## Правила подключения (обязательные)

Выведены из разбора живого проекта 2026-07-28: 23 366 событий и 2 368 отчётов
показали, что аналитика была подключена «вроде правильно», а ответов не давала.
Каждое правило ниже — оплаченная ошибка, а не вкусовщина.

**1. Событие без срезов бесполезно.** Запись из `ts/sid/name` отвечает «сколько»,
но никогда — «почему». Ставь `stamp_device=True` и `stamp_cookies` с первого дня:
User-Agent и куки приходят в каждом запросе даром, а без них «мобильный конвертит
вдвое хуже» видно только в Метрике, где нет ни твоих денег, ни A/B.

**2. Штампуй на КАЖДОМ событии, не только на визите.** Сессия может начаться до
выкатки или потеряться (приватный режим, чищеный localStorage). Тогда по срезу
разложится часть воронки — а это хуже, чем никакой, потому что выглядит как правда.

**3. Плечо A/B — такой же срез.** Панель A/B считает назначения и оплаты, но не
показывает, ГДЕ плечо теряет людей. На вопрос «вариант проигрывает — он отпугивает
на превью или на кнопке оплаты?» отвечает только срез по воронке.

**4. Имя не из конфига теряется молча.** `/api/goal` отвечает `200 OK` и не пишет
ничего. Фронт может слать событие месяцами — в дашборде его просто нет. Модуль
теперь считает такие имена и называет их в `/admin/selfcheck` и на странице
красной строкой; `selfcheck.ok=false`, пока они есть. **После каждой новой
`goal(...)` на фронте — открой selfcheck.**

**5. Страницы ПОСЛЕ оплаты — отдельный слой, и обычно там аналитики нет вовсе.**
Личный кабинет, страница отчёта, спасибо-страница живут вне общего шаблона.
Апселлы там дают самую быструю выручку, а в дашборде их не видно.
Подключая, **переопредели `visitEvent`**: иначе `visit` полетит и оттуда,
знаменатель воронки раздуется уже оплатившими, и конверсия сайта поедет вниз
на ровном месте.

**6. Не держи две системы целей.** Если на странице есть прямые
`ym(id,'reachGoal',…)`, замени их на `Analytics.goal(…)` — он шлёт и в Метрику,
и к нам. Оставишь оба — цели Метрики задвоятся.

**7. Реестр платежей обязан нести срезы.** Сумма/тариф/вариант отвечают «сколько
денег», но не «от кого». Клади в запись платежа устройство, тип объекта, регион и
id заказа/отчёта — иначе «мобильные платят меньше?» проверяется только по событиям,
где нет сумм. Писать надо на ЗАКАЗЕ в момент создания: к моменту оплаты запроса от
браузера уже нет, человек возвращается со шлюза.

**8. Собирай JS-ошибки.** Без них сломанный на одном браузере скрипт выглядит как
«этот сегмент почему-то не платит». `analytics.js` шлёт `js_error` сам (error +
unhandledrejection, не больше трёх на загрузку) — добавь имя в `signal_labels`.

**9. Меряй дочитывание страницы.** Ниже первого экрана про человека не известно
ничего, а «не убедился» и «не долистал» лечатся по-разному.

**10. Заведи здоровье источников, если продаёшь данные.** Доля проверок, где
источник не ответил, по дням. Иначе о деградации узнаёшь из жалоб: у нас 6,5%
оплаченных отчётов уходили без главной проверки, и это не было видно нигде.

**11. Срез считай по предмету сделки, а не по посетителю.** Регион по IP отвечает
«откуда смотрят», а нужно «что покупают»: человек из Москвы проверяет дом в Сочи,
и ставку двигать надо по второму.

**12. Проверь Метрику на мёртвые цели.** Цель с нулём достижений за месяц — либо
её нет в коде, либо имя разошлось. Отдельно посмотри, не оптимизируется ли на неё
кампания: автостратегия на мёртвой цели слепа.

### Ловушки браузера (проверено вживую, стоило двух переписываний)

- **`IntersectionObserver` ненадёжен для замеров.** Его колбэки привязаны к
  отрисовке кадров: в невидимой/фоновой вкладке не приходит ни одного, а в другом
  прогоне события пришли по два раза. Для «долистал до блока» считай прокрутку
  обычным обработчиком.
- **`requestAnimationFrame` для троттлинга — та же ловушка.** Кадры не
  отрисовываются — замер не делается. Троттли `setTimeout`.
- **Порог «видно N% площади блока» не работает**, если блок выше экрана телефона:
  такая доля не набирается никогда. Считай по линии — «верх блока поднялся выше
  75% экрана».

## Хранилище
`{data_dir}/analytics_events.jsonl` — по одной строке на событие. Локально,
автономно, переживает рестарты (в volume проекта).

## Новый проект — порядок подключения
1. Скопировать `analytics.py`, `analytics_render.py` в модули проекта, `analytics.js` в static.
2. Прописать `AnalyticsConfig` со своей воронкой/событиями + `include_router`.
   Сразу задать `stamp_device=True` и `stamp_cookies` — см. правила 1–3.
3. Расставить `Analytics.goal(...)` по фронту в точках воронки.
4. Подключить `analytics.js` на страницы ПОСЛЕ оплаты со своим `visitEvent` (правило 5).
5. Открыть `/admin/selfcheck?token=…`: `ok=true`, в `rejected` пусто, у шагов воронки
   `seen>0`. Пока это не так — подключение не закончено, а не «почти готово».
Проект сразу автономен и имеет свой `/admin/stats`.

## Проверки, что имплементировали верно

Пайплайн сам себя проверяет на трёх уровнях — не полагаемся на «вроде подключил».

**1. Валидация конфига (fail-fast при старте).** `make_router(cfg)` вызывает
`cfg.validate()` и **падает с ValueError**, если конфиг битый (нет funnel, шаг не
пара, нечисловой price_variant, data_dir не пишется), а на подозрительное
(пустой admin_token, роль на событие вне funnel/extra_events) печатает warning.
То есть криво собранный конфиг не доедет до прода молча.

**2. Self-check живого проекта — `GET /admin/selfcheck?token=…`.** Показывает:
валиден ли конфиг (errors/warnings), пишется ли хранилище (событий/сессий),
**wiring** — по каждому объявленному событию сколько раз оно реально пришло
(`seen=0` на шаге = фронт в этой точке не подключён), и **`rejected`** — имена,
которые фронт слал, а сервер отбросил, потому что их нет в конфиге. Второе важнее
первого: незаявленное событие теряется молча, с ответом `200 OK`, и обнаружить
пропажу больше нечем. Пока `rejected` непуст, `ok=false`, а на самом дашборде
висит красная строка с именами. Счётчик живёт в памяти — считает с последнего
рестарта, чего для диагностики подключения достаточно.

**3. Проверочные тесты.**
- `test_analytics.py` — 27 unit-тестов ядра (классификация объекта, валидация,
  воронка+дедуп, отвал/медиана, денежная петля+bump, NET-маржа+CB-rate, лифт,
  LTV, трение, since, self-check, разбор User-Agent, потерянные события). Быстрые, без сети:
  `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest test_analytics.py -q`
- `smoke.py` — round-trip против ЖИВОГО проекта после вендоринга:
  `python3 smoke.py https://проект.ru <ADMIN_TOKEN>` — проверяет selfcheck,
  приём `/api/goal` и что событие долетает до дашборда. Запускать после деплоя
  в новый проект — подтверждает, что интеграция рабочая end-to-end.
